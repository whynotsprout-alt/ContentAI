# 取消邮箱验证流程设计

## 目标

ContentAI 不再将邮箱验证作为注册、登录或密码重置的前置条件。用户完成注册后直接回到登录页，仍通过密码重置邮件找回账号。禁用账号的安全边界保持不变。

## 采用方案：兼容性下线

新注册用户一律创建为 `active`，并在创建时写入 `email_verified_at`。注册接口仅返回注册成功提示；Web 端将用户带回登录页，不再显示“检查邮箱”状态或重发入口。

登录不再检查验证开关、`email_verified_at` 或 `pending_verification` 状态。为避免旧数据遗留在已废弃流程中，密码正确且账号未禁用的历史用户会在成功登录时被规范化为 `active`，并补写缺失的 `email_verified_at`。禁用账号仍返回禁止访问，不会被该兼容逻辑恢复。

密码重置维持现状：忘记密码仍仅向已存在、未禁用的账号发送重置邮件；重置令牌仍是一次性且有时效；重置密码仍会撤销既有会话。它不依赖邮箱验证字段。

## API 与前端边界

Web 端删除 `/verify-email` 路由、验证页面分支、自动验证请求、注册后的邮件确认状态、重发冷却和 `resendVerification` 调用。认证 API 客户端不再公开验证与重发方法。

为给旧客户端和旧邮件链接提供确定的迁移信号，后端暂时保留 `POST /api/auth/verify-email` 与 `POST /api/auth/resend-verification` 两个路由，但统一返回 `410 Gone` 及“邮箱验证已停用”的结构化错误，不生成或消费验证令牌，也不发送验证邮件。文档将它们标记为弃用接口，不属于支持的认证流程。

## 配置与生产限制

`require_email_verification`、验证令牌有效期和验证邮件重发限制不再属于有效认证配置。生产启动校验反向约束：若环境显式尝试启用邮箱验证，应用拒绝启动；正常生产配置无需 SMTP 才能完成注册或登录。SMTP 仍可为密码重置邮件配置，缺失时仅在实际发送重置邮件时按现有邮件后端策略处理。

验证令牌用途和邮件发送代码从正常注册路径移除。数据库中现有验证相关列和历史令牌不做破坏性删除，避免与既有数据库和审计数据不兼容；新流程不会创建验证令牌。

## 测试与验收

- 注册创建可立即登录的活跃用户，且不投递验证邮件。
- 历史待验证用户在密码正确时可登录并被规范化；禁用用户仍无法登录。
- 忘记密码和重置密码邮件流程仍可用，并会撤销旧会话。
- 两个保留的验证端点返回 `410`，不造成状态或邮件副作用。
- Web 路由、认证视图和 API 客户端不再暴露验证或重发入口；注册成功后导航到登录页。
- 配置测试覆盖生产环境拒绝开启邮箱验证，并确认生产不因缺少验证专用 SMTP 配置而拒绝启动。
- API、架构/运维文档和前端契约测试反映上述边界。

## 不在范围内

- 删除数据库中的 `email_verified_at`、`pending_verification` 历史值或验证令牌记录。
- 改变禁用账号、登录失败锁定、会话管理或密码策略。
- 增加新的账户激活或邀请流程。
