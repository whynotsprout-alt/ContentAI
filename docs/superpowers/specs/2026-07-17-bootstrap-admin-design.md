# 启动引导管理员与环境变量整理设计

## 目标

新部署在首次启动后自动拥有一个可登录、已激活的管理员账号；管理员凭据由部署环境提供。同步移除已经下线的邮件功能配置，并将环境变量按职责归类。

## 已确认的行为

- 使用已有的 bootstrap 管理员概念，不要求管理员先通过 HTTP 注册接口注册。
- 仅当指定邮箱尚不存在时创建账号；不会在服务重启时重置既有用户的密码、角色或状态。
- 新建账号的邮箱已验证、状态为 `active`、角色为 `admin`。
- 原来的 `BOOTSTRAP_ADMIN_EMAILS` 仍用于将手工注册的匹配邮箱赋予管理员角色，保持兼容；新增单个默认管理员凭据用于首次创建。
- 密码仅作为启动时的初始凭据，不写入日志、响应或文档示例的真实值。
- 邮件验证和密码重置接口继续返回 410，不重新引入邮件配置。

## 配置接口

~~~dotenv
CONTENTAI_AUTH__BOOTSTRAP_ADMIN_EMAIL=admin@example.com
CONTENTAI_AUTH__BOOTSTRAP_ADMIN_PASSWORD=replace-with-a-long-unique-password
~~~

- 邮箱为空时不执行自动创建。
- 配置了邮箱但没有密码时，服务启动失败并明确指出缺失的密码变量。
- 生产环境要求这两个变量均存在。
- 密码使用现有 `pwdlib` 哈希器后写入 `AppUser.password_hash`，不会以明文入库。

## 启动流程

~~~text
数据库初始化完成
        |
AuthService.bootstrap_default_admin(session)
        |
邮箱用户是否存在？ -- 是 --> 不修改，继续启动
        |
       否
        |
创建 active + verified + admin 用户，提交事务
        |
注册其他运行时服务，应用就绪
~~~

将创建操作放在 `init_database()` 之后、服务注册之前，可保证表已经存在，且应用对外就绪前账号已可登录。

## 环境文件整理

- `.env.example` 按“基础运行时、服务连接、应用、模型与代理、搜索、认证”分组。
- `.env` 保留当前部署需要的值，去掉被代码忽略的邮件变量和重复覆盖项；敏感值不进入模板或文档。
- 只保留被当前设置模型或 Docker Compose 实际消费的非默认覆盖项；默认值留在代码和模板说明中，减少本地环境漂移。

## 测试与验证

- 服务启动会创建管理员；该账号可用初始凭据登录。
- 重复启动不会再创建用户，也不会更改已有密码或角色。
- 缺失配对的默认管理员配置会被设置验证拒绝。
- 现有注册 bootstrap 管理员行为不回退。
- 执行认证、应用生命周期、API 合约与配置相关测试，之后重建 Compose 服务并检查健康状态。
